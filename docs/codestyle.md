# Стиль C++

Проект использует C++20 и описанные ниже правила оформления.
Проверка форматирования выполняется clang-format **18.1.8**:

```sh
python3 tools/check_style.py
python3 tools/check_style.py --fix
```

Форматируются только `.cpp` и `.hpp` в `src/`. Тесты исключены из форматирования.
Целостность зафиксированного набора тестов проверяется
отдельно: `python3 tools/verify_original_tests.py`.

## Форматирование

- UTF-8, переводы строк LF, четыре пробела; продолжение строки — восемь пробелов.
- Ширина строки — 120 символов. Фигурные скобки открываются на следующей строке.
- `public`, `protected`, `private` выровнены с объявлением класса; внутри — один отступ.
- Содержимое пространства имён не получает дополнительного отступа.
- `const` стоит перед типом; `*` и `&` относятся к типу: `const Map& map`.
- Условие записывается как `if (condition)`, циклы — `for(...)`, `while(...)`,
  выбор — `switch(...)`. Тела условий заключаются в фигурные скобки.
- Список инициализации конструктора начинается на следующей строке;
  двоеточие остаётся в строке объявления конструктора.
- Заголовки идут от общих к локальным: системные, внешние библиотеки, другие
  компоненты проекта, тот же компонент, соответствующий заголовок `.cpp`.
  Последние две группы определяются скриптом по расположению файла.

`.clang-format` задаёт отступы и расположение конструкций. Для полной проверки,
включая порядок заголовков, используется `tools/check_style.py`.

## Имена и интерфейсы

Файлы именуются в `snake_case`, C++-заголовки имеют расширение `.hpp` и
`#pragma once`. Компоненты сгруппированы в пространства имён по назначению:
например, `app`, `model`, `view` и `http_handler`.
Внутренние функции единицы трансляции размещаются в анонимном
пространстве имён.

Типы, функции и методы именуются в `PascalCase`; название метода описывает действие.
Параметры, локальные переменные и открытые поля используют `snake_case`.
Закрытые и защищённые поля имеют префикс `m_`. Внешние контракты сохраняют
обязательные имена: например, `operator()`, `std::hash`, сериализация Boost и
точки расширения стандартной библиотеки. Имена в HTTP API не зависят от стиля C++.

Объекты и поля инициализируются при объявлении. Предпочтительны `const`, RAII,
`enum class`, именованные константы и явное владение ресурсами. Входные данные
передаются константными, изменяемые выходные параметры располагаются после них.
Параметры, передающие владение, принимаются по значению или rvalue-ссылке без
`const`, чтобы сохранить семантику перемещения; это явно указывается в контракте.
Методы, не меняющие состояние, помечаются `const`; переопределения — `override`.
У полиморфного интерфейса должен быть виртуальный деструктор. Непрозрачная реализация
(pImpl) применяется, когда скрывает существенную внешнюю зависимость.

## Документация и читаемость

Классы, функции и методы имеют комментарии Doxygen. Контракт публичного метода
описывается в заголовке: назначение, ограничения входа, владение и существенные
ошибки. Комментарий объясняет причину или обязательство, а не повторяет имя метода.
Для внутренних помощников комментарий находится возле определения.

```sh
doxygen Doxyfile
```

HTML-документация появляется в `build/docs/html/index.html`, XML — в
`build/docs/xml/`. Doxygen проверяет также закрытые методы, статические функции и
локальные классы; пропущенная документация считается ошибкой.

Читаемость кода поддерживают одна ответственность на метод, явные инварианты,
ранние выходы при ошибках, небольшая глубина вложенности и имена, отражающие смысл.
Чистые вычисления отделяются от HTTP, БД и файловой системы. Дополнительный шаблон
проектирования вводится для конкретной границы ответственности.

Форматтер не проверяет архитектуру, корректность владения, смысл имён, отсутствие
«магических» значений, допустимость сравнений вещественных чисел и присваиваний в
условиях. Он также не гарантирует длину неделимых строковых литералов и URL.
Они требуют ручной проверки и тестирования. Изменения `const` и добавленные скобки
обязательно проверяются компиляцией.
