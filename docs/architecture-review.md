# Архитектурное ревью — 4 октября 2026

Ревью охватывает доменную модель, прикладные операции, HTTP-контроллеры,
представление JSON, PostgreSQL, снимки, конфигурацию, запуск, потоки и зависимости
сборки. Проверялись направление зависимостей, владение объектами, инварианты
коллекций, обработка отказов и возможность тестировать компоненты отдельно.

Выбранная структура MVC с отдельным прикладным слоем подходит этому серверу.
Репозиторий уже отделяет SQL от игровых операций. Основные проблемы оказались
в жизненном цикле объектов, согласованности состояния и границах обработки ошибок.
Ниже зафиксированы замечания к состоянию до ревью и внесённые исправления.

## Существенные замечания и исправления

### 1. P1 — исключение фонового обработчика могло аварийно завершить процесс

В `main.cpp` рабочие `jthread` напрямую вызывали `io_context::run`. Исключение
из автоматического тика, SQL или записи снимка выходило за пределы функции потока
и вызывало `std::terminate`. Если исключение попадало в главный поток, присоединение
других потоков могло ждать незавершённые операции: сигналов и приёма соединений
достаточно, чтобы контекст не закончился сам.

Добавлен `infrastructure/http/run_workers.h`: рабочие потоки сохраняют первое
исключение, останавливают контекст, присоединяются, затем передают ошибку главному
потоку. Он печатает причину и возвращает код 1. Это контролируемая остановка при
фатальном отказе, а не автоматическое восстановление подключения к БД.
После такого отказа финальное сохранение не выполняется, чтобы не заменять
последний успешный снимок состоянием частично выполненной операции.

Проверки: исключение при одном и четырёх рабочих потоках; реальный процесс
с недоступным каталогом фонового снимка завершился с кодом 1, без `abort`.

### 2. P1 — операции над HTTP-соединением начинались из разных strand

`RequestHandler` выполняет API в игровом strand. Ответ из него напрямую запускал
`SessionBase::Write`, хотя чтение, таймер и обработчики завершения принадлежат
strand сокета. Последовательная обработка игры не обеспечивает последовательность
операций отдельного соединения.

`Write` теперь передаёт начало записи исполнителю сокета через `dispatch`.
Ответ и объект сессии удерживаются до завершения записи. Игровая логика остаётся
в собственном strand, а сетевой поток управляет своим соединением.

Проверки: настоящий HTTP, 48 параллельных подключений, 40 параллельных тиков,
проверка длины ответа и повторный прогон с санитайзерами. ThreadSanitizer не запускался;
отсутствие всех возможных гонок этими проверками не доказано.

### 3. P1 — владение картами не соответствовало указателям в сессиях

`Game` хранил карты в `vector`, а сессии — указатели на его элементы. Добавление
карты после создания сессии могло переместить элементы и сделать указатель висячим.
Неявное копирование `Game` также копировало индексы с указателями на объекты
исходной игры, а не новой копии.

Карты переведены в `deque`, сохраняющий адреса при добавлении в конец. Копирование
`Game` запрещено; перемещение сохранено. Проверяется, что карта добавляемой сессии
действительно принадлежит этой игре. Для чтения сессий добавлен const-доступ.

Проверка: после входа игрока добавлены 200 карт, адрес карты и дальнейший тик остаются
корректными. Копирование `Game` запрещено проверкой времени компиляции.

### 4. P1 — восстановление снимка могло оставить частичное состояние или упасть

Восстановление добавляло сессии непосредственно в целевую игру. Несуществующая
карта, сессия или собака из файла могли привести к разыменованию `nullptr`.
Ошибка после загрузки первой сессии оставляла часть данных уже опубликованной.
Положение собаки за пределами дорог позднее приводило к обращению к пустому
результату поиска ближайшей дороги.

Теперь снимок восстанавливается во временную игру. Проверяются ссылки на карты,
сессии и собак, принадлежность собаки сессии, конечность координат и положение
на дороге. Только после успешной проверки игра и игроки перемещаются в целевые
объекты; отсутствие исключений при этих присваиваниях закреплено `static_assert`.
Восстановление выполняется до создания прикладного слоя, в игру без активных сессий.
Дополнительно поиск дороги сообщает о неверном состоянии вместо обращения к пустой коллекции.

Проверки: неизвестная карта после корректной сессии, отсутствующая сессия,
отсутствующая собака и координаты вне дорог. При каждом отказе целевая игра
сохраняет прежние карты и не получает частично загруженных сессий.
Порядок и типы полей существующего формата снимка не изменены.

### 5. P2 — коллекции и индексы могли расходиться

Повторный ID собаки, сессии или токен игрока перезаписывал индекс, но добавлял
ещё один объект в коллекцию. Один игрок становился доступен по токену, а другой
оставался в перечислении. При загрузке ID не по порядку счётчики дополнительно
увеличивались вместо вычисления следующего свободного значения.

Добавлены проверки уникальности ID, токенов, сессии карты и связи игрок–собака.
Индексы откатываются, если следующее добавление в коллекцию выбрасывает исключение.
Счётчики вычисляются как `max(текущее, id + 1)`; значения за поддерживаемым диапазоном
отклоняются до изменения коллекций. Создание собаки использует `make_shared`.

Проверки: отклонение дубликатов без изменения количества и адресов объектов;
порядок ID `20, 2` даёт следующий ID `21` для сессий, собак, предметов и игроков.

### 6. P2 — callback завершения сессии удерживал адрес Application

Сессия могла пережить `Application`, но callback содержал его `this`.
Следующий тик обращался к уничтоженному объекту. Это нарушало границу владения:
модель, игроки и репозиторий могут жить дольше обслуживающего их приложения.

Привязка callback собрана в одном методе. Он захватывает непосредственно зависимости
игры, игроков и репозитория; адрес `Application` больше не нужен. Неявное копирование
`Application` запрещено. Зависимости обязаны жить всё время обработки тиков —
их срок жизни задаёт `main.cpp`.

Проверка: после уничтожения приложения тик завершает игрока и записывает результат
в ещё существующий репозиторий. Прогон с AddressSanitizer также проходит.

### 7. P2 — причины ошибок смешивались, внутренние сообщения выдавались клиенту

Прикладной слой перехватывал любой `std::invalid_argument`, пришедший из обновления
мира. В том числе ошибка реализации репозитория могла превратиться в сообщение
о неверном времени запроса и HTTP 400. Остальные исключения возвращались клиенту
в виде полного `what()`, включая внутренние сведения инфраструктуры.

Для некорректного игрового времени введён отдельный `model::InvalidTimeDelta`.
Общие операции ручного и автоматического тика объединены в один закрытый метод.
Внутренние ошибки дают HTTP 500 с фиксированным текстом; подробности передаются
через внедрённый обработчик диагностики. В рабочем сервере он пишет журнал.

Проверка: репозиторий намеренно выбрасывает `invalid_argument`. HTTP-ответ — 500,
диагностическая строка доступна обработчику журнала, но отсутствует в ответе;
авторизация игрока не удаляется до успешного сохранения результата.

### 8. P2 — неудачная запись снимка считалась успешной для таймера

`StateStore::OnTick` обновлял `last_save_` до записи файла. Если запись падала,
следующий вызов ожидал целый период, хотя последнего сохранения не произошло.
Теперь отметка обновляется после успешной записи и переименования файла.

Проверка: первый вызов с отсутствующим каталогом завершается ошибкой; после создания
каталога вызов с нулевым приращением времени повторяет запись. Сохранён исходный
строгий порог `elapsed > period`. В автоматическом режиме фатальная ошибка останавливает
сервер согласно пункту 1; повтор относится к повторному вызову StateStore, а не
к незаметному продолжению работы фонового таймера.

### 9. P2 — зависимости сборки скрывали связь контроллера с сетевой реализацией

`RequestHandler` включал целиком сервер сокетов, а одна библиотека содержала
контроллеры, транспорт и журнал. Это позволяло незаметно протащить инфраструктурные
зависимости в HTTP-адаптер приложения и усложняло независимую сборку компонентов.

Выделены `game_controller`, `game_transport`, `game_logging`. Контроллер знает
HTTP-протокол и прикладные операции; транспорт не включает контроллеры. Сохранился
интерфейсный target `game_http`, объединяющий их для существующих потребителей.
Платформенный заголовок вынесен в `common`.

Добавлена проверка `tools/check_architecture.py`: прямые локальные include внутри
common, domain, application, view и controller должны соответствовать разрешённым
направлениям. Она выполняется в CTest. Это проверка локальных include, а не полный
анализ всех транзитивных зависимостей и использования сторонних библиотек.

## Оценка остальных границ

| Область | Оценка |
| --- | --- |
| Domain | Не зависит от HTTP, JSON, SQL или файлов. Модель остаётся изменяемой и рассчитана на последовательные обращения. |
| Application | Управляет сценариями, авторизацией и завершением игрока. DTO ответов отделяют представление от изменяемых объектов. |
| MVC | JSON-представление уместно для API. Самостоятельный слой HTML-шаблонов или универсальный базовый контроллер здесь не нужны. |
| Repository | Интерфейс скрывает SQL, запись результата использует транзакцию, тесты подставляют реализацию в памяти. Дополнительный общий CRUD-репозиторий не нужен. |
| Configuration | Преобразует внешний JSON в модель и задаёт начальные параметры. Метаданные отображения карт отделены от игровых сущностей. |
| Snapshot | Сериализация находится в инфраструктуре; восстановление проверяет связи до публикации состояния. |
| Composition root | main связывает реализации и определяет сроки жизни. Управление потоками вынесено в отдельно проверяемый компонент. |
| Code style | Форматирование централизовано. Старые тесты исключены из содержательных правок. Все 29 заголовков компилируются самостоятельно. |

## Ограничения и возможное развитие

Это однопроцессный сервер с одной последовательной очередью игровых операций.
Синхронный PostgreSQL может задерживать тики при медленном запросе. Для большей
нагрузки потребуется отдельная стратегия выполнения БД и ограничение очереди,
с сохранением порядка завершения игроков. Добавление пула соединений само по себе
не делает доменную модель потокобезопасной.

Снимок активной игры и таблица рекордов не образуют общую транзакцию. Отказ в середине
тика не откатывает весь мир, а потеря ответа на COMMIT не обеспечивает exactly-once
запись результата. Для строгих гарантий при сбоях потребуется устойчивый ID завершения,
идемпотентная запись и журнал операций/outbox либо хранение состояния в одной БД.
Текущее ревью не вводит такую новую модель сохранения и не заявляет этих гарантий.

Существующий снимок сбрасывает движение и счётчики времени при восстановлении;
исторические особенности HEAD и разбора query-параметров закреплены тестами.
Их изменение потребует отдельной версии протокола/формата и согласованной миграции.

Крупный `model.h`, глобальный тип Token и смешение имён model/domain можно разделить
и унифицировать при дальнейшем развитии. Это улучшения сопровождения, менее важные
сейчас, чем исправленные нарушения владения и обработки ошибок.
